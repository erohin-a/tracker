mkdir server, server\templates, server\fonts, client, certs
Шаг 3. Генерация секретов
Откройте PowerShell:
powershell
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
python -c "import secrets; print(secrets.token_urlsafe(48))"
python -c "import secrets; print(secrets.token_urlsafe(48))"
Создайте файл D:\tracker\.env:
text
SECRET_ENCRYPTION_KEY=<первый ключ>
JWT_SECRET=<второй ключ>
ADMIN_API_KEY=<третий ключ>
Сохранить без BOM (UTF-8). Ключ ADMIN_API_KEY — это пароль для входа в /admin.
Шаг 4. Создание TLS-сертификата
powershell
cd D:\tracker\certs
& "C:\Program Files\OpenSSL-Win64\bin\openssl.exe" req -x509 -newkey rsa:4096 `
  -keyout privkey.pem -out fullchain.pem -days 365 -nodes `
  -subj "/CN=localhost" `
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1,IP:<ваш_IP>" `
  -addext "basicConstraints=critical,CA:TRUE"
Для прода — заменить на Let's Encrypt или корпоративный.
Шаг 5. Запуск сервера
powershell
cd D:\tracker
docker compose up -d --build
Start-Sleep -Seconds 25
docker compose ps
Три контейнера должны быть Up.
Шаг 6. Первичная настройка админки
Откройте https://localhost/admin/login
Логин admin, пароль = ADMIN_API_KEY
Перейдите в Отделы — создайте структуру (Бухгалтерия, Разработка, Продажи…)
Перейдите в Сотрудники — добавьте всех сотрудников с 1C ID
Перейдите в Календарь — проверьте год, отметьте праздники, сохраните
Перейдите в Настройки — проверьте: часовой пояс, начало рабочего дня, idle-порог
Перейдите в Компьютеры — выпустите bootstrap-токены для каждого ПК
Шаг 7. Резервное копирование (рекомендую)
Создайте D:\tracker\backup.bat:
bat
@echo off
cd /d D:\tracker
docker compose exec -T db pg_dump -U tracker tracker > backup_%date:~-4%%date:~3,2%%date:~0,2%.sql
Настройте в Планировщике задач Windows — ежедневно в 03:00.

5.3. Для кадровика / руководителя
Как получить отчёт по конкретному сотруднику:
Открыть https://localhost/admin/reports
Период: нажать «Этот месяц» (или задать вручную)
Отделы — выбрать нужный отдел, или оставить пустым
Сотрудники — Ctrl+клик выбрать одного или нескольких
Группировка:
«Рабочие дни ? Сотрудник» — табель по дням
«Месяц ? Сотрудник» — сводка за месяц
Формат: XLSX ? нажать «Сформировать»
Скачается файл — открывается в Excel
Как читать отчёт:
Рабочий день — дата с учётом настройки «начало дня». Если сотрудник начал работу в 06:00 или позже — это день старта. Если раньше (например, в 02:00) — это предыдущий день.
Отработано — от старта первой сессии до конца последней за день (включает перерывы)
Эффективно — фактическая активность без пауз > 5 минут
1C ID — идентификатор сотрудника в учётной системе
Как определить, что сотрудник работал:
Отработано ? 8:00 — нормальный день
Эффективно = 6-7 часов при 8-часовом дне — нормально (перерывы, обед, разговоры)
Эффективно < 3 часов при большом «Отработано» — сотрудник присутствовал у ПК, но не работал
Много аварийных закрытий — клиент падает, сообщить администратору
Отчёты для бухгалтерии:
Формат XLSX
Группировка «Месяц ? Сотрудник»
Длительности уже в формате [ЧЧ]:ММ:СС — Excel считает как время
Дата в колонках Год/Месяц/Число — готова для сводных таблиц

5.4. Для сотрудника (установка и работа)
Что вам дадут:

Дождаться завершения ? поставить галочку «Запустить Tracker» ? «Готово»
После этого откроется окно регистрации. Если вы вставили токен в установщике — оно закроется автоматически и сразу откроется главное окно.
Первый запуск:
В окне регистрации вставьте bootstrap-токен (Ctrl+V)
Нажмите «Зарегистрировать»
Если всё хорошо — увидите сообщение «Компьютер успешно зарегистрирован»
Откроется главное окно с кнопками
Ежедневная работа:
Начало рабочего дня:
Клиент запускается сам при включении ПК (или ярлык на рабочем столе)
Откройте окно из трея (иконка рядом с часами)
Нажмите ? Начать работу
Кнопка станет серой, «Конец работы» — активной
Приступайте к работе
Во время работы:
Клиент работает в фоне, ничего не блокирует
Окно можно свернуть в трей (крестиком)
Кнопки старт/стоп также доступны в трее (правый клик)
Конец рабочего дня:
Откройте окно
Нажмите ? Конец работы
Подтвердите
Закрывать клиент не обязательно — он сам закроет сессию при выходе из системы
Что важно знать:
Если вы ушли, забыв нажать «Конец работы» — сессия закроется сама через 30 минут (или другое значение, установленное администратором), причём временем последней активности
Данные об активности отправляются раз в 30 секунд
Если интернета нет — данные копятся локально, отправятся при появлении связи
Содержимое нажатий клавиш НЕ записывается — только счётчики
При выключении ПК клиент сам корректно закрывает сессию
Что делать, если:
Иконки нет в трее — запустить ярлык Tracker из меню «Пуск»
Ошибка «Регистрация» — токен уже использован, обратиться к администратору
Статус «Офлайн» — нет связи с сервером, данные копятся локально
Клиент упал — запустить заново, при следующем запуске сессия закроется как аварийная и данные отправятся
Автозапуск:
По умолчанию клиент запускается при входе в систему. Если не нужен — снять галочку в главном окне. Поставить обратно можно так же.
Приватность:
Собираются только:
счётчик нажатий клавиатуры (без символов)
клики и скролл мыши
имя приложения и заголовок активного окна
НЕ собираются:
содержимое нажатий
скриншоты экрана
пароли

Проблема	Причина	Решение
getaddrinfo failed в Python	Windows резолвит localhost в ::1, Docker Desktop IPv6 плохо пробрасывает	В client/.env — https://127.0.0.1
.env не читается	python-dotenv искал в Path.cwd(), а там серверный .env	Переписали config.py: сначала client/.env
create_all не мигрирует схему	SQLAlchemy create_all создаёт только новые таблицы	Ручной ALTER TABLE или (план) Alembic
records/batch ? 500	Дубликаты record_uid от разных ПК	Ищем дубликаты по всей таблице, обёртка try/except
sessions ? 409	Сессия принадлежит другому ПК после перерегистрации	Возвращаем 200, игнорируем принадлежность
audit_log.entity_id переполнялся	Список UUID через запятую не влезал в VARCHAR(64)	Кладём только первый UUID, всё в new_value
500 на дашборде	Не передавался cutoff_online в шаблон	Добавили в контекст
PDF ? 500 NameError: Paragraph	Импорт был внутри другой функции	Импорт внутри _pdf_table_data
localhost в браузере vs Python	Разное поведение резолвинга	В браузере localhost, в Python 127.0.0.1
Порт 80 занят Windows	HTTP.sys (IIS/WinRM)	Только 443 в nginx
Русские буквы в PDF	Стандартные шрифты reportlab не поддерживают кириллицу	DejaVuSans.ttf в server/fonts/

ЧАСТЬ 1. Что у нас получилось — трезвый анализ
1.1. Сильные стороны
Архитектурно система получилась правильной:
Разделение ответственности. Клиент собирает, сервер хранит и считает, админка показывает. Никаких «толстых клиентов» и логики в UI.
Офлайн-first. Локальная SQLite + WAL + синхронизация с backoff — это то, что делают взрослые системы (Hubstaff, Toggl), а не самоделки.
HMAC-подпись записей. Это редкость для самописных систем. Защищает от подмены данных на лету и от «переигрывания» трафика.
Bootstrap-токены. Правильный подход — новый ПК нельзя зарегистрировать без ведома админа.
Аудит. Все действия администратора логируются. Это база для 152-ФЗ.
Разделение секретов. SECRET_ENCRYPTION_KEY (Fernet для client_secret в БД), JWT_SECRET (для сессий), ADMIN_API_KEY (для входа в админку). Каждый для своей задачи.
Идемпотентность. record_uid и session_uid уникальны, повторная отправка не создаёт дублей. Это критично для офлайн-режима.
Веб-интерфейс. От SQL-запросов вручную мы ушли к полноценной панели с 11 страницами.
Функционально закрыто почти всё базовое ТЗ:
Сбор активности (клавиатура, мышь, активное окно, idle)
Регистрация ПК
Сессии с кнопками старт/стоп

1.2. Слабые стороны и риски
Технические:
Нет Alembic. Каждое изменение схемы — ручной ALTER TABLE через psql. На проде это лотерея: забудешь колонку — упадёт 500 при первом обращении к ней. Рано или поздно это выстрелит.
Один администратор. ADMIN_API_KEY — единый пароль. Если уволенный сотрудник знал его — доступа не отобрать без смены ключа (что ломает всех клиентов, см. документацию). Нет ролей, нет истории входов в админку.
Нет тестов. Мы правим код «на глаз», и каждый патч может сломать соседнюю функцию. Это видно по истории чата: то dashboard упал, то PDF NameError, то segments не те.
Логи клиента только локально. Если у удалённого сотрудника что-то упало — админ узнает только по звонку «ничего не работает».
Нет алертов. ПК офлайн 3 часа — никто не знает. Батч не проходит 20 минут — никто не знает.
Партиционирование записей отсутствует. При 50+ ПК таблица records за год станет десятками миллионов строк. Поиск по ней замедлится.
Операционные:
Нет установщика. Сотрудник не поставит систему сам — нужен Python, venv, активация, ручной запуск. Для распространения на 20 ПК это блокер.
Нет бэкапов по расписанию. Если volume pgdata умрёт — все данные уйдут. Потеря месяца работы.
Нет политики хранения данных. Данные копятся вечно. По 152-ФЗ должны быть определены сроки хранения и процедура уничтожения.
Юридические:
152-ФЗ не оформлен. Согласие сотрудников, приказ, уведомление РКН, описание мер защиты (ст. 19). Без этого — формально внедрять нельзя.
1.3. Общая оценка
Система готова на ~75%:
Готово к тестовой эксплуатации на 5–10 сотрудниках в одной комнате, где админ рядом.
Не готова к распространению на 20+ сотрудников в разных офисах (нет установщика, алертов, ролей).
Не готова к официальному внедрению без юридической обвязки.
Ключевое: то, что уже есть — работает. Это очень хорошая база, на которой можно докрутить оставшиеся 25% за 3–5 дней.

Показ статуса сессии в трее. Сейчас иконка просто есть — а хорошо бы менять её цвет в зависимости от того, идёт сессия или нет (зелёная — работаем, серая — простой, красная — нет связи). Одно движение глаз — и понятно.

Горячая клавиша. Например, Ctrl+Shift+S — старт/стоп без открытия окна. Мелочь, но для тех, кто работает в полноэкранных приложениях, удобно.
Автопродолжение сессии. Если сотрудник работает за ПК, но забыл нажать «Старт» после перезагрузки — клиент может сам предложить «Продолжить вчерашнюю сессию?». Опционально.
Ярлык «Пауза». Иногда нужно отойти на 15 минут — сейчас только «Конец работы», а он закрывает сессию. Пауза была бы удобнее: сессия идёт, но с пометкой «перерыв» в отчёте.
Тултип на панели. Наведи на «Эффективно» — подсказка: «Активное время без пауз длиннее 5 минут». Меньше вопросов к админу.
Смена темы. Светлая/тёмная. Сейчас жёстко светлая. Сотрудники, работающие ночью, оценят.
Проверка обновлений с уведомлением. Сейчас обновление — редко. Хорошо бы: клиент раз в сутки проверяет версию, если есть новая — показывает «Доступно обновление до 1.3.0. Установить сейчас / Позже».

ЧАСТЬ 3. Напоминание о старте работы — обсуждение
Твоя идея правильная: самая частая проблема в таких системах — забыли нажать «Старт». Утром начали работать, вспомнили к обеду, кнопку нажали, но 4 часа — в пропасть. Отчёт показывает «3 часа», а реально человек работал 7.
3.1. Как это должно работать
Условие для напоминания:
Клиент запущен, зарегистрирован, но активная сессия не идёт (active_session пустой), и при этом есть активность на клавиатуре/мыши за последние N минут.
Ключевой момент: напоминание не должно выскакивать, когда сотрудник просто не работает — например, пришёл, включил ПК, пошёл пить кофе. Напоминать нужно только когда есть признаки работы без активной сессии.
То есть логика такая:
Клиент запущен, сессии нет.
Фиксируется активность (нажатие клавиши, движение мыши) дольше threshold_minutes подряд.
Показываем напоминание.
3.2. Варианты «как часто напоминать»
Ты предложил: однократно / каждую минуту / каждые 10 минут / каждый час. Хорошо, но я бы добавил нюансы:
Правильнее сделать три параметра:
Порог срабатывания — сколько минут работы без сессии до первого напоминания. Например: 15 минут. (По умолчанию — 15, настраивается.)
Интервал повторов — если проигнорировали, напоминать снова каждые: 1 / 5 / 10 / 30 / 60 минут.
Максимум напоминаний — сколько раз за день максимум. Например: 5 раз. Чтобы не превратилось в спам, если сотрудник принципиально не хочет запускать сессию.
Итого настройки:
Параметр	Значения	По умолчанию
Порог «есть активность, но нет сессии»	5 / 10 / 15 / 30 / 60 мин	15 мин
Интервал повторов	однократно / 1 / 5 / 10 / 30 / 60 мин	10 мин
Максимум напоминаний за день	1 / 3 / 5 / 10 / без ограничений	5
3.3. Как выглядит напоминание

Плюс — мигание иконки в трее, чтобы привлечь внимание.
3.4. Где хранить настройки
Три варианта, обсудим:
А. В серверных настройках (AppSetting). Плюс: единая политика для всех. Минус: клиент должен регулярно подтягивать (уже умеет раз в 5 минут). Если сотрудник уже превысил лимит напоминаний, а админ изменил настройки — применится при следующем цикле.
Б. В локальных настройках (config.json клиента). Плюс: можно настроить под каждого сотрудника индивидуально. Минус: сотрудник может отключить сам — то есть контроля нет.
В. Гибрид (рекомендую). Основные параметры — на сервере (чтобы админ мог заставить). Плюс — локальный тумблер «не беспокоить сегодня», который действует до конца дня. Так сотрудник не отключит навсегда, но если у него встреча и он не хочет видеть toast — заглушит на время.
Моя рекомендация: вариант В.
3.5. Технические детали для реализации
На клиенте есть CollectorWorker, который уже знает про активность — но он работает только когда сессия активна. Для напоминания нужен отдельный лёгкий слушатель активности, который работает всегда.
Проще: расширить CollectorWorker так, чтобы он мог работать в «пассивном режиме» (только фиксировать факт активности, не записывая записи в БД).
Или добавить отдельный маленький ActivityWatcher в главном потоке клиента — pynput позволяет навесить второй listener на клавиатуру/мышь без конфликта.
Напоминание — это QSystemTrayIcon.showMessage() (нативный тост Windows) или собственный QDialog с Qt.Tool и Qt.WindowStaysOnTopHint. Я бы выбрал нативный тост — он менее навязчив.
3.6. Что важно НЕ делать
Не блокировать работу. Никаких «пока не нажмёшь — не закроется». Это бесит и провоцирует саботаж.
Не напоминать, когда сессия идёт. Очевидно, но проверять.
Не напоминать в нерабочие часы. Если сейчас суббота — не надо.
Не считать активностью скролл в браузере. Иначе будет напоминание, когда сотрудник читает новости. Только клавиатура + клики + движение мыши.

ЧАСТЬ 4. Удаление данных на сервере — обсуждение
Хороший вопрос. Сейчас удалить что-либо можно только через прямой SQL, что опасно и неудобно. Причины для удаления:
Тестовые данные. Мы завели тестового сотрудника, отправили тестовую сессию — она теперь в отчётах.
Ошибочная регистрация. Зарегистрировали ПК не тому сотруднику или перерегистрировали — появились «мёртвые» сессии, которые висят и не отправляются.
Дубли. Два ПК с одним хостнеймом.
Право на забвение (152-ФЗ). Сотрудник уволился, требует удалить все его данные.
4.1. Что именно нужно уметь удалять
Разные сценарии — разные «кнопки»:
Сценарий 1: удалить одну сессию.
Тестовая сессия на 2 минуты, попала в отчёт. Открываю список сессий на странице сотрудника, жму «Удалить» — сессия и все её записи уходят.
Сценарий 2: удалить все сессии тестового сотрудника.
Завели тестового, поигрались, теперь надо снести. Открываю карточку — «Удалить все сессии и записи».
Сценарий 3: удалить все сессии за период.
С 1 по 5 сентября мы что-то тестировали. Выбираю период, жму «Удалить всё за период» (с фильтром по сотруднику или по ПК).
Сценарий 4: удалить все данные по ПК.
ПК перерегистрировали 3 раза, накопилось мусора. Открываю ПК — «Удалить все сессии и записи этого ПК».
Сценарий 5: удалить сотрудника полностью.
Увольнение + требование удалить всё. «Удалить сотрудника и все его данные».
4.2. Soft delete vs hard delete
Это важный вопрос. Два подхода:
Soft delete — данные помечаются как is_deleted = true, но физически остаются в БД. Плюс: можно восстановить, аудит цел. Минус: БД растёт, отчёты должны везде фильтровать is_deleted = false.
Hard delete — данные удаляются физически, каскадно. Плюс: чисто. Минус: необратимо, при ошибке — конец.
Моя рекомендация: двухступенчатая схема.
Кнопка «Удалить» — soft delete. Данные скрываются из отчётов, но остаются в БД с флагом.
Раз в сутки (или по кнопке «Очистить удалённые») — планировщик физически удаляет всё, что помечено is_deleted больше 30 дней назад. За это время можно «ой, я не то удалил» и восстановить.
Исключение — только для полного удаления сотрудника по 152-ФЗ: сразу hard delete, с записью в audit_log «Удалено по требованию субъекта ПДн».
4.3. Как это выглядит в UI
Добавляем на страницы:
/admin/employees/{id} — карточка сотрудника с историей сессий. Кнопки: «Удалить сессию» (у каждой), «Удалить все сессии», «Удалить сотрудника полностью».
/admin/computers/{id} — карточка ПК с сессиями. Кнопка «Удалить все данные ПК».
/admin/sessions — новая страница «Сессии» с фильтрами и массовыми действиями: чекбоксы, «Удалить выбранные», «Удалить всё по фильтру».
/admin/reports — опция «Показать удалённые» (для админа). По умолчанию скрыты.
Важно: все удаления — с записью в audit_log. Кто, когда, что, сколько записей.
4.4. Риски, о которых надо помнить
Каскадное удаление. Если удалить сессию — что делать с её записями? Правильно: удалить и их. Но это может быть 100k+ строк, нужно делать батчами.
Связи с отчётами. Если отчёт сформирован и сохранён — там данные останутся, а в БД уже нет. Нужно решить: отчёты — это «снимок» или «живой запрос»? У нас — живой, значит после удаления отчёт покажет меньше данных. Это нормально.
Race condition. Если сотрудник сейчас отправляет данные, а админ удаляет сессию — что произойдёт? Нужно блокировать удаление активных сессий или отправлять клиенту команду revoke.
Право на забвение. По 152-ФЗ сотрудник может требовать удаления. Нужно уметь удалять всё про конкретного человека — с ФИО, 1C ID, всеми сессиями, записями, привязками ПК. С подтверждением через ввод ФИО руками (чтобы не удалили случайно).

ЧАСТЬ 5. Рост базы и политика хранения
Данные копятся. Оценим скорость роста:
Один ПК в час активности:
activity записи: раз в 5 секунд ? 720/час
window записи: при смене окна, в среднем 30–60/час
idle записи: редко, ~5/час
Итого ~800 записей/час ? 8 часов = ~6400 записей/день на одного сотрудника.
50 сотрудников ? 6400 = 320 000 записей в день. Или ~10 миллионов в месяц. За год — 120 миллионов записей.
Для PostgreSQL это не смертельно, но:
Без индексов — плохо.
Индексы у нас есть (ix_records_computer_ts, ix_records_session).
При партиционировании по месяцам — работает нормально.
5.1. Стратегия — обсудим варианты
Вариант 1. Хранить всё вечно.
Плюс: всегда есть история. Минус: БД пухнет, бэкапы становятся огромными, отчёты за 2 года замедляются.
Вариант 2. Полное удаление по возрасту.
Всё, что старше N месяцев, удаляется. Плюс: просто. Минус: теряем историю. Для 152-ФЗ, кстати, обычно рекомендуют хранить 1–3 года.
Вариант 3. Агрегация + удаление сырых (моя рекомендация).
Сырые данные (records) храним 3 месяца.
Сессии (work_sessions) храним 2 года.
Агрегированная дневная статистика — навсегда.
Логика: сырые данные нужны для отладки и точных отчётов «что делал в 10:15». Но по-настоящему они нужны только за последние пару месяцев. Для годовых отчётов достаточно агрегата: «Иванов за 15.09 отработал 8:23, эффективно 6:47, топ-3 программы: PyCharm / Chrome / Telegram».
Вариант 4. Архив в отдельной таблице.
Старые сырые данные переносим в records_archive (та же схема, но в другой таблице, без индексов для скорости вставки). При необходимости конкретный месяц можно «поднять» обратно. Но это усложняет.

5.3. Партиционирование — важно
При 100+ млн записей обычная таблица начнёт замедляться. Решение — PostgreSQL native partitioning по месяцу client_ts.
Что это даёт:
Удаление старого месяца = DROP TABLE records_2025_09 — мгновенно, а не DELETE на миллион строк.
Запросы по диапазону дат сканируют только нужные партиции.
Схема:
text
records_2026_01
records_2026_02
records_2026_03
...
PostgreSQL сам маршрутизирует вставку в нужную партицию по client_ts.
Реализовать сейчас, пока данных мало — легко. Позже, когда 50 млн строк — больно.
5.4. Бэкапы
Отдельный вопрос, но связан с ростом:
Full backup — раз в неделю, pg_dump полностью.
Incremental — не поддерживается «из коробки» в PostgreSQL, но можно WAL-архивирование.
Проще: ежедневный pg_dump с ротацией 30 дней. Для БД до 10 ГБ это работает.
