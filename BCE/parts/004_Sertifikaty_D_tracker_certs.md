## 1. Назначение и цели

### 1.1. Назначение системы

Система «Трекер» предназначена для автоматизированного учёта рабочего времени и производительности удалённых сотрудников. Система состоит из двух модулей:

- **Клиентский модуль** — устанавливается на рабочий компьютер сотрудника, собирает данные об активности и отправляет их на сервер.
- **Серверный модуль** — работает на сервере компании, принимает данные, хранит их, предоставляет веб-интерфейс для управления и формирования отчётов.

### 1.2. Цели системы

- Фиксация времени начала и окончания работы сотрудника.
- Учёт активных программ и времени работы в них.
- Учёт времени активной работы с клавиатурой и мышью (без записи содержимого нажатий).
- Накопление данных при отсутствии интернет-соединения и синхронизация при его появлении.
- Формирование отчётов по одному, нескольким или всем сотрудникам за произвольный период.
- Экспорт отчётов в форматы TXT, PDF, XLS.
- Редактирование и объединение данных на серверной стороне.
- Интеграция с системой 1С (опционально).

### 1.3. Целевая аудитория и условия эксплуатации

- **Количество сотрудников:** до 50 (при использовании SQLite) или более (при использовании PostgreSQL).
- **Операционные системы клиента:** Windows 10/11, Linux (X11; поддержка Wayland ограничена — см. раздел 3.2.5).
- **Операционная система сервера:** Linux (Ubuntu 22.04 LTS или аналог).
- **Тип развёртывания:** локальный сервер компании или облачный хостинг.

## 3. Клиентский модуль

### 3.1. Интерфейс пользователя

#### 3.1.1. Поля ввода данных о сотруднике

| Поле | Тип | Обязательность | Валидация | Описание |
|------|-----|---------------|-----------|----------|
| Фамилия | Текстовое | Да | 1–50 символов, только буквы, дефис | Вводится при первом запуске |
| Имя | Текстовое | Да | 1–50 символов, только буквы, дефис | Вводится при первом запуске |
| Отчество | Текстовое | Нет | 1–50 символов, только буквы, дефис | Вводится при первом запуске |

**Важно:** Все поля должны проходить валидацию на стороне клиента. При вводе недопустимых символов (цифры, спецсимволы) — показывать сообщение об ошибке. Данные сохраняются в `config.json` в директории пользователя.

#### 3.1.2. Кнопки управления работой

- **«Начало работы»** — запускает трекинг. Кнопка становится активной (зелёный фон), кнопка «Конец работы» — неактивной (серый фон).
- **«Конец работы»** — останавливает трекинг. Кнопка становится активной (зелёный фон), кнопка «Начало работы» — неактивной.
- **Взаимоисключение:** Одновременно активной может быть только одна кнопка. Состояние кнопок сохраняется при перезапуске приложения.
- **Защита от случайного нажатия:** При нажатии «Конец работы» — показать диалоговое окно подтверждения («Вы уверены, что хотите завершить рабочий день?»).

#### 3.1.3. Кнопка автозапуска

- **«Автозапуск»** — переключатель (toggle). Включённое состояние — клиент запускается при входе пользователя в систему.
- **Реализация:**
  - **Windows:** запись в реестр `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run`.
  - **Linux:** создание `.desktop`-файла в `~/.config/autostart/`.
- **Визуальное отображение:** Текущее состояние отображается текстом («Включён» / «Выключен») и цветом (зелёный / серый).
- **Права:** Изменение автозапуска может требовать прав администратора (особенно на Windows). Предусмотреть обработку отказа в доступе.

#### 3.1.4. Индикатор статуса синхронизации

Блок «Последнее подключение к серверу» содержит:

| Элемент | Описание | Обновление |
|---------|----------|-----------|
| Дата и время последней успешной синхронизации | Формат: `ДД.ММ.ГГГГ ЧЧ:ММ` | При каждой успешной синхронизации |
| Количество несинхронизированных записей | Целое число | Каждые 30 секунд |
| Статус-индикатор | Зелёный — данные актуальны; жёлтый — есть несинхронизированные данные; красный — нет соединения | Каждые 30 секунд |
| Текстовое предупреждение | Если данные не передавались более 1 часа: «Данные не передавались с ДД.ММ.ГГГГ ЧЧ:ММ». Отображается красным цветом | Каждую минуту |

**Дополнительно:** Добавить индикатор состояния трекинга (активен / остановлен) в системном трее.

#### 3.1.5. Системный трей (рекомендуемое расширение)

- Клиентский модуль должен сворачиваться в системный трей при закрытии окна (а не завершать работу).
- Контекстное меню в трее:
  - «Открыть» — развернуть окно.
  - «Начать работу» / «Завершить работу» — быстрые действия.
  - «Отправить данные» — ручная синхронизация.
  - «Выход» — полное завершение приложения.
- **Реализация (PyQt6):** `QSystemTrayIcon` + `QMenu`.
- **Реализация (Tkinter):** библиотека `pystray` + `PIL`, запуск в отдельном потоке с `run_detached=True`.

### 3.2. Сбор данных

#### 3.2.1. Уникальный идентификатор компьютера

- **Генерация:** UUID v4 при первом запуске.
- **Сохранение:** В `config.json` в директории пользователя.
- **Дополнительные идентификаторы:** MAC-адрес (получение через `uuid.getnode()`) + хеш имени машины (`platform.node()`).
- **Проблема:** При клонировании системы UUID может скопироваться. **Решение:** При первом запуске проверять наличие `computer_id` в файле; если файл отсутствует — генерировать новый UUID. При синхронизации сервер может обнаружить дубликат и уведомить оператора.

#### 3.2.2. Время включения и отключения компьютера

- **Время включения:** Получение через `psutil.boot_time()`. **Важно:** `psutil.boot_time()` на Windows может давать некорректный результат при пробуждении из спящего режима. **Решение:** Использовать `psutil.boot_time()` в сочетании с `wmi` (Windows) или `/proc/uptime` (Linux) для перекрёстной проверки.
- **Время отключения:** Фиксация через обработчик сигналов завершения (`signal.SIGTERM`, `signal.SIGINT`). **Проблема:** При аварийном завершении (BSOD, отключение питания) время не будет зафиксировано. **Решение:** При следующем запуске клиента сравнивать последнее известное время работы с текущим; если разрыв превышает порог — создавать запись о завершении сессии с пометкой «Аварийное завершение».

#### 3.2.3. Название активной программы

**Проблема:** `pygetwindow.getActiveWindow().title` возвращает заголовок окна, а не имя процесса. Заголовок может меняться (например, «Документ1 — Word» ? «Документ2 — Word»), что приведёт к созданию множества ложных записей.

**Решение:** Использовать комбинацию:

```python
import win32gui
import win32process
import psutil

hwnd = win32gui.GetForegroundWindow()
_, pid = win32process.GetWindowThreadProcessId(hwnd)
process = psutil.Process(pid)
process_name = process.name()  # Например, "chrome.exe"
window_title = win32gui.GetWindowText(hwnd)  # Например, "Документ1 — Word"
```

Для Linux (X11):

```python
from Xlib import display, X
import psutil

d = display.Display()
window = d.get_input_focus().focus
wm_name = window.get_wm_name()
pid = window.get_full_property(d.intern_atom('_NET_WM_PID'), X.AnyPropertyType)
process = psutil.Process(pid.value[0])
```

**Рекомендация:** Хранить как `process_name` (стабильный идентификатор), так и `window_title` (для контекста). Группировать программы по `process_name`.

#### 3.2.4. Время работы в активной программе

- **Период опроса:** 5 секунд (настраивается в `config.json`).
- **Логика:**
  - Если `process_name` не изменился — таймер текущей программы увеличивается.
  - Если `process_name` изменился — создаётся новая запись.
  - Если пользователь бездействует (нет ввода) более 60 секунд — таймер программы приостанавливается (но не сбрасывается).
- **Проблема:** Частое переключение окон (Alt+Tab) может создать множество коротких записей. **Решение:** Агрегировать записи с одинаковым `process_name` в пределах одной сессии.

#### 3.2.5. Время работы на клавиатуре и мыши

- **Механизм:** `pynput.keyboard.Listener` и `pynput.mouse.Listener`.
- **Подсчёт времени:**
  - Каждое событие (нажатие клавиши, движение/клик мыши) фиксируется с таймстемпом.
  - «Время работы на клавиатуре» — суммарная длительность интервалов, в которых были нажатия. Если разрыв между нажатиями превышает 60 секунд — интервал не учитывается.
  - Аналогично для мыши.
- **Содержимое нажатий НЕ записывается.**
- **Проблема с Wayland (Linux):** Wayland намеренно блокирует прямой доступ к клавиатуре. `pynput` не будет работать под Wayland без специальных разрешений. **Решение:**
  - Предупредить пользователя при запуске на Wayland.
  - Рекомендовать использовать X11 (Xorg).
  - Альтернатива: использовать `evdev` для доступа к `/dev/input/event*` (требует прав root или добавления пользователя в группу `input`).
- **Проблема с правами (Linux):** Для доступа к `uinput` может потребоваться запуск от root. **Решение:** Создать udev-правило, разрешающее доступ группе пользователей.
- **Проблема с macOS:** macOS ограничивает мониторинг клавиатуры. Требуется явное разрешение в «Настройках безопасности и конфиденциальности» ? «Универсальный доступ». (macOS не является целевой ОС, но упоминается для полноты.)

#### 3.2.6. Обработка бездействия

- **Порог бездействия:** 60 секунд (настраивается).
- **Механизм:** Отслеживать время последнего события клавиатуры/мыши. Если `now - last_event > inactivity_timeout`, считать пользователя неактивным.
- **Важно:** Время бездействия не вычитается из общего времени сессии, но не учитывается в времени активности клавиатуры/мыши.
- **Реализация:** Использовать `idle_time` (кроссплатформенная библиотека) или собственный счётчик на основе событий `pynput`.

### 3.3. Локальное хранение данных

#### 3.3.1. Структура базы данных SQLite

```sql
CREATE TABLE IF NOT EXISTS records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    uuid TEXT UNIQUE NOT NULL,           -- UUID записи для синхронизации
    type TEXT NOT NULL,                   -- 'session', 'program_usage', 'activity'
    session_uuid TEXT,                    -- Ссылка на сессию (для program_usage и activity)
    computer_id TEXT NOT NULL,
    employee_last_name TEXT NOT NULL,
    employee_first_name TEXT NOT NULL,
    employee_middle_name TEXT,
    data TEXT NOT NULL,                   -- JSON-сериализованные данные записи
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_synced BOOLEAN DEFAULT FALSE,
    synced_at TIMESTAMP
);

CREATE INDEX idx_is_synced ON records(is_synced);
CREATE INDEX idx_created_at ON records(created_at);
CREATE INDEX idx_session_uuid ON records(session_uuid);
```

**Обоснование:** Использование JSON для поля `data` позволяет гибко менять схему без миграций. Поле `uuid` обеспечивает идемпотентность при повторной отправке.

#### 3.3.2. Режим WAL и конкурентный доступ

- **Включить режим WAL:** `PRAGMA journal_mode=WAL;`
- **Установить таймаут блокировки:** `PRAGMA busy_timeout=5000;` (5 секунд).
- **Обоснование:** WAL позволяет читателям и писателям работать параллельно, что критически важно при одновременной записи из потока сбора данных и чтении из потока синхронизации.
- **Проблема:** WAL-файлы могут накапливаться при аварийном завершении. **Решение:** При запуске клиента выполнять `PRAGMA wal_checkpoint(TRUNCATE);`.

### 3.4. Синхронизация с сервером

#### 3.4.1. Алгоритм синхронизации

```
1. Проверить наличие интернет-соединения (GET /api/health с таймаутом 5 сек).
2. Если соединение есть:
   a. Выбрать все записи с is_synced = FALSE (батчами по 100 записей).
   b. Сформировать JSON-пакет.
   c. Отправить POST /api/sync с заголовком Authorization: Bearer <token>.
   d. Если ответ 200 OK:
      - Пометить записи из accepted_uuids как is_synced = TRUE, synced_at = NOW().
      - Обновить индикатор синхронизации.
   e. Если ответ 401 Unauthorized:
      - Обновить токен (refresh token).
      - Повторить попытку.
   f. Если ответ 5xx или таймаут:
      - Повторить с экспоненциальной задержкой (1, 2, 4, 8, 16 секунд; максимум 5 попыток).
3. Если соединения нет:
   - Ничего не делать. Повторить через 5 минут.
```

#### 3.4.2. Повторные попытки (Retry Policy)

Использовать библиотеку `tenacity`:

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
import httpx

@retry(
    stop=stop_after_attempt(5),
    wait=wait_exponential(multiplier=1, min=1, max=16),
    retry=retry_if_exception_type((httpx.TimeoutException, httpx.ConnectError)),
    reraise=True
)
async def send_batch(batch: list[dict]) -> dict:
    async with httpx.AsyncClient(timeout=30.0) as client:
        response = await client.post(
            f"{server_url}/api/sync",
            json={"computer_id": computer_id, "employee": employee, "records": batch},
            headers={"Authorization": f"Bearer {token}"}
        )
        response.raise_for_status()
        return response.json()
```

**Обоснование:** Экспоненциальная задержка с джиттером предотвращает «забивание» сервера при массовых сбоях.

#### 3.4.3. Батчинг (пакетная отправка)

- **Размер батча:** 100 записей (настраивается).
- **Причина:** Уменьшение количества HTTP-запросов, снижение нагрузки на сервер и сеть.
- **Ограничение:** Общий размер JSON-пакета не должен превышать 1 МБ. При превышении — уменьшать батч.

#### 3.4.4. Идемпотентность

- Каждая запись имеет уникальный `uuid`.
- Сервер при получении записи с существующим `uuid` игнорирует её (не создаёт дубликат).
- Это позволяет безопасно повторять отправку при сбоях.
