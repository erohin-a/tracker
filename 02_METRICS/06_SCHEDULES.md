## Назначение
Описать шаблоны графиков работы: зачем нужны, как устроены, как привязываются к отделам и сотрудникам, что уже реализовано и что ещё предстоит. Это карта для администратора, который настраивает плановое время, и для разработчика, который дорабатывает отчёты по опозданиям.

## Содержание

### Что такое график работы
- **График (Schedule)** — шаблон планового режима труда: начало и конец рабочего дня, обед, рабочие дни недели, пороги опоздания и переработки.
- Хранится в таблице `schedules`.
- Один график может применяться к нескольким отделам и сотрудникам.
- Иерархия приоритета:
  1. Если у сотрудника задан `schedule_id` — используется его график.
  2. Иначе — график отдела (`departments.schedule_id`).
  3. Если нигде не задан — дефолт (Пн–Пт, 09:00–18:00).

### Модель `Schedule`
| Поле | Тип | Описание |
|---|---|---|
| `id` | Integer, PK | |
| `name` | String(128), unique | Название графика |
| `description` | Text | Описание (опционально) |
| `is_active` | Boolean | Активен ли график |
| `work_start_minute` | Integer | Начало рабочего дня в минутах от 00:00 |
| `work_end_minute` | Integer | Конец рабочего дня в минутах от 00:00 |
| `late_threshold_minutes` | Integer | Порог опоздания в минутах |
| `overtime_threshold_minutes` | Integer | Порог переработки в минутах |
| `flexible_hours_per_day` | Integer | Гибкий график (часов в день). 0 = обычный |
| `lunch_enabled` | Boolean | Учитывать ли обед |
| `lunch_start_minute` | Integer | Начало обеда в минутах (nullable) |
| `lunch_end_minute` | Integer | Конец обеда в минутах (nullable) |
| `work_mon` … `work_sun` | Boolean | Рабочие дни недели |
| `created_at` | DateTime | |

**Почему минуты, а не строки «09:00»:** проще сравнивать, сортировать и считать. При отображении — конвертация в `HH:MM`.

### Форма графика (`schedule_form.html`)
**Поля:**
- Название (обязательно, ≥ 2 символов).
- Описание (опционально).
- Начало рабочего дня: часы + минуты.
- Конец рабочего дня: часы + минуты.
- Обед: чекбокс «Учитывать», начало и конец.
- Рабочие дни недели: 7 чекбоксов (Пн–Вс).
- Порог опоздания (минуты).
- Порог переработки (минуты).
- Гибкий график (часов в день), 0 = обычный.

**Валидация (`_parse_schedule_form`):**
- Название ≥ 2 символов.
- Время в диапазоне 00:00–23:59.
- Конец рабочего дня позже начала.
- Конец обеда позже начала.
- Выбран хотя бы один рабочий день.
- Пороги и гибкие часы — неотрицательные числа, гибких ≤ 24.
- Уникальность имени графика.

### Список графиков (`schedules.html`)
Показывает:
- Название графика.
- Рабочие часы (`HH:MM–HH:MM`).
- Рабочие дни (сокращённо).
- Обед (если включён).
- Гибкий график (если > 0).
- Сколько сотрудников и отделов используют (`employees_count`, `departments_count`).
- Кнопки: «Изменить», «Удалить».

**Удаление запрещено, если график используется** — возвращается ошибка `in_use_{emp}_{dept}`. Сначала нужно отвязать.

### Привязка к отделам и сотрудникам
- **Отдел:** поле `departments.schedule_id` (FK на `schedules.id`).
- **Сотрудник:** поле `employees.schedule_id` (FK на `schedules.id`).
- **Где редактируется:**
  - Сотрудник: в форме редактирования на `/admin/employees` — выпадающий список «График» (опция «как в отделе» = пусто).
  - Отдел: в модели есть поле, но **UI для привязки графика к отделу не реализован** (нет формы на `/admin/departments`).

### Что уже реализовано
- Модель `Schedule` со всеми полями.
- CRUD-роуты и шаблоны (`schedules.html`, `schedule_form.html`).
- Валидация формы.
- Отображение «Сколько сотрудников/отделов используют».
- Запрет удаления используемого графика.
- Выбор графика при редактировании сотрудника.

### Что НЕ реализовано
- **UI для привязки графика к отделу.** Поле `departments.schedule_id` есть в модели, но формы нет.
- **Отчёт «Опоздания/переработки».** Сравнение фактического старта с плановым временем графика не считается.
- **Учёт обеда в метриках.** Обед хранится, но в отчётах не вычитается.
- **Гибкий график.** Поле есть, но логика не реализована.
- **Применение графика к календарю.** Рабочие дни недели в графике не пересекаются с `calendar_days`.
- **Отображение графика у сотрудника.** В карточке сотрудника график виден только в форме редактирования.

### Планируемые отчёты на основе графиков
- **«Опоздания/переработки»** — сравнение `session_start` с `work_start_minute + late_threshold_minutes`, а `session_end` с `work_end_minute + overtime_threshold_minutes`.
- **«План/факт»** — сравнение плановых часов (по графику) с фактическими (Отработано).
- **«Гибкий график»** — контроль отработки N часов в день без фиксированного времени начала.

### Пример работы (после реализации)
**Дано:** график «Офис 09:00–18:00», обед 13:00–14:00, порог опоздания 15 мин.
**Сотрудник начал работу в 09:20.**
- Опоздание = 20 минут > 15 → в отчёте «Опоздания» строка с флагом.
- Обед: если сотрудник работал с 13:00 до 14:00 без паузы — это может считаться переработкой (логика ещё не определена).

## Ключевые решения
- **График — отдельная сущность.** Не привязан жёстко к отделу, может переиспользоваться.
- **Иерархия: сотрудник → отдел → дефолт.** Классический подход, гибко для разных случаев.
- **Минуты от 00:00** вместо строк — удобнее для вычислений.
- **Пороги опоздания/переработки — на уровне графика.** Разные отделы могут иметь разные правила.
- **Удаление используемого графика запрещено.** Защита от «висячих» ссылок.
- **Гибкий график — поле есть, логика в планах.** Не блокирует MVP.
- **UI привязки к отделу — в планах.** Сотрудник уже привязывается, отдел — нет.
