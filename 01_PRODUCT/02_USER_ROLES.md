## Назначение
Описать пять ролей пользователей админки, их права, механику ограничения доступа и текущее состояние реализации.

## Содержание

### Пять ролей
| Роль | Код | Назначение |
|---|---|---|
| Администратор | `admin` | Полный доступ к системе |
| Оператор | `operator` | Ежедневная работа с данными, без администрирования |
| Кадровик | `hr` | Сотрудники, отделы, графики |
| Руководитель отдела | `manager` | Отчёты только по своему отделу |
| Наблюдатель | `viewer` | Только просмотр отчётов |

### Механика ограничения доступа
- Роль хранится в `admin_users.role` (String(32)).
- Роль попадает в сессию при логине (`request.session["admin_user"]["role"]`).
- В шаблонах — переменная `admin_role`, доступна через context processor.
- Sidebar в `base.html` оборачивает группы пунктов в `{% if admin_role in (...) %}`.
- Декоратор `_require_admin_role(request)` — 403, если роль не `admin`.
- Для `manager` — поле `AdminUser.department_id` (FK на `departments.id`). При показе списков/отчётов применяется фильтр по отделу.

### Особенности роли manager
- Видит только данные своего отдела.
- Если `department_id` не задан — видит всё (страховка от «пустого» менеджера).
- Фильтрация сотрудников, сессий, отчётов — через `manager_department_id(user)` и хелперы.
- В форме создания/редактирования пользователя — выпадающий список отделов, показывается только при выборе роли `manager`.

### Особенности ролей hr и viewer
- `hr` — ограничен справочниками и отчётами, без технической части.
- `viewer` — read-only: отчёты и дашборд, без изменений.

## Ключевые решения
- Роли заданы жёстко в коде (`ROLES_INFO` в `security_passwords.py`), а не в БД — так проще для 5 фиксированных ролей.
- Начальный пользователь — `admin` / `ADMIN_API_KEY` из `.env` (при первом запуске).
- Смена роли пользователя — через админку `/admin/users/{id}/edit`.
- Удаление последнего активного `admin` — запрещено (проверка `_active_admins_count`).
